# 🧪 Self-Logic-Lab-Boot

**基于 Spring Boot 3 & Java 17，记录那些杂七乱八但有用的逻辑碎片。**

---

## 🏗️ 核心架构：三层数据流转协议

本项目采用严谨的三层模型，确保数据在不同层级间的高效、安全流转：

### 1. BaseResult - 统一响应契约
所有 RESTful 接口的终点。
- **作用**: 规范 JSON 结构，包含 `code`, `msg`, `data` 三大核心字段。
- **价值**: 降低前后端对接成本，确保全局异常响应与正常响应结构完全对齐。

### 2. ServiceResult<T> - 业务逻辑载体
Service 层与 Controller 层的核心通信协议。
- **特性**:
  - 通过 `isSuccess()` 快速进行逻辑分支判断，无需比对状态码。
  - 采用静态工厂方法模式 (如 `success()`, `failure()`)，提升代码逻辑表达力。
- **价值**: 彻底解耦业务状态与 HTTP 状态码，使 Service 层代码具备更强的可移植性和纯粹性。

### 3. ServicePageDataResult<T> - 分页数据容器
专为复杂查询与大批量数据展示设计。
- **特性**: 严格封装 `total` (总条数) 与 `dataList` (结果集)。
- **价值**: 解决了分页场景下多余字段传递的混乱，为前端组件提供标准、预期的分页数据格式。

> #### 💡 架构总结：全栈通用的数据契约
> **项目深度复用此套数据格式，构建了从数据库到前端的“无损通信隧道”：**
> * **标准契约**：前端解析逻辑只需对接一套 `BaseResult` 结构，实现一次封装，处处调用。
> * **逻辑闭环**：`ServiceResult` 承载业务语义，`BaseResult` 承载协议语义，两者配合实现“逻辑防腐”，新模块可零成本接入此套体系。
> * **分页标准**：通过 `ServicePageDataResult` 沉淀了标准分页元数据格式，极大提升前后端联调效率。

## 🛠️ 分页请求核心逻辑：BaseLimitRequest

项目针对分页场景开发了 **“双模自动转换”** 机制，这是对传统分页逻辑的一次优雅下沉：

- **自动逻辑转换**:
  覆写 `getPageNumber()` 方法。该方法自动返回 (SQL Offset)。实现了从“用户页码”到“数据库偏移量”的透明转换。
- **精准分组校验**:
  利用 `jakarta.validation` 的分组特性，同一 DTO 支持两套校验规则：
  - `@Validated(PageGroup.class)`：专注于页码模式校验。
  - `@Validated(OffsetGroup.class)`：专注于下标模式校验。

> #### 💡 设计总结：从“业务逻辑”到“物理执行”的优雅桥接
> **分页基类通过内部转换机制，实现了对复杂 SQL 计算逻辑的屏蔽：**
> * **逻辑闭环**：杜绝了手动计算带来的边界逻辑漏洞。
> * **多态校验**：引入分组校验逻辑，使同一个请求对象能够完美适配“移动端无限滚动（下标模式）”与“管理后台（页码模式）”两种不同场景，极大地提升了 DTO 的复用率。
> * **参数防御**：在基类中完成参数合法性防御，确保进入 Service 层的每一个分页参数都是“干净”且“可信”的。

## 🔍 全链路追踪体系：BusinessLogFilter

项目集成了生产级的日志监控方案，通过“日志 + 响应”的双向绑定，实现问题的秒级定位。

### 1. 全链路 TraceID 闭环
利用 `SLF4J MDC` (Mapped Diagnostic Context) 机制，在请求进入时自动生成唯一的 `selfTraceId`。
- **日志端**: 每一行业务日志（Controller/Service/Mapper）都会自动打印该 ID。
- **客户端**: 响应体 `BaseResult` 自动携带该 ID，实现“凭证式”排查。

### 2. 报文全兼容捕获
基于 `ContentCachingRequestWrapper` 深度定制，完美解决 Spring 中流只能读取一次的问题：
- **全类型支持**: 自动识别并聚合 `GET参数`、`Form表单` 及 `@RequestBody (JSON)` 报文。
- **安全截断**: 内置 `MAX_BODY_SIZE` 保护机制，防止超大报文导致内存溢出。

> #### 💡 运维总结：从“盲盒”到“透明”
> **该模块赋予了系统“自解释”能力：**
> * **异常溯源**：前端报错只需反馈 `selfTraceId`，开发者即可在日志中瞬间检索出该请求的全部上下文。
> * **性能监控**：通过日志中的 Time 字段，可直观发现系统中的“慢接口”，为系统重构提供数据支撑。

## 🔐 安全防御机制：ParamValidationInterceptor

为了防止请求在传输过程中被恶意篡改，项目引入了基于 **参数重排 + MD5摘要** 的验签拦截器。

### 1. 签名生成协议
- **数据规范化**: 拦截器自动提取 `QueryString`、`Form` 及 `JSON Body` 报文，并使用 `TreeMap` 进行 **字典序(ASCII码)** 重排。
- **加盐机制**: 拼接过程中引入服务端私留的 `SIGN_SALT`，有效防止攻击者通过彩虹表反向破解摘要。
- **时效防御**: 强制校验 `selfCheckTIme` 参数，超过 30 秒的请求将被视为过期。

### 2. 核心校验维度
- **零成本跨域**: 采用标准参数传递凭证（如 `?selfValidation=xxx`），完美兼容浏览器跨域环境，避免了自定义 Header 带来的预检请求成本。
- **流式穿透**: 结合 `ContentCachingRequestWrapper` 实现了对 JSON 内容的无损提取，确保了 Body 数据的一致性校验。

> #### 💡 安全总结：构建纵深防御体系
> **拦截器与过滤器的协同工作，为系统提供了坚实的防护层：**
> * **完整性校验**：通过对全量参数的重排拼接，任何一个字符的变动都会导致验签失败。
> * **可确定性算法**：字典序重排解决了由于前端传参顺序不确定导致的“误报”问题。
> * **无感介入**：安全验证逻辑完全下沉至基础设施层，业务 Controller 无需编写任何校验代码。
